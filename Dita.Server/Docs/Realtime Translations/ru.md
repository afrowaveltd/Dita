# Переводы в реальном времени

Этот документ существует в качестве живого тестового ввода для конвейера автоматического перевода. Любое изменение этого файла запускает повторный перевод всех файлов целевого языка на следующем запланированном запуске.

## Обзор архитектуры

Трансляционный конвейер был реструктурирован в модульную архитектуру с четырьмя специализированными подсервисами, координируемыми легким оркестратором:

- **BackendTranslationService** — оркеструет весь конвейер, обрабатывает валидацию сервера и делегирует работу субсервисам.
- **CountriesTranslationService** — синхронизирует названия стран из словарей на один язык.
- **LocalizationTranslationService** — обнаруживает добавленные/удаленные ключи в JSON-словаре по умолчанию и переводит их на целевые языки.
- **DocumentsTranslationService** — переводит файлы документации Markdown с отслеживанием каждого блока и метаданными.

Каждая подслужба работает независимо и сообщает о прогрессе через SignalR в режиме реального времени.

## Что делает служба

Сервис работает по расписанию и выполняет пятиступенчатый конвейер: валидация сервера, синхронизация страны, синхронизация словаря JSON, перевод файлов Markdown и сохранение результатов. Каждый этап излучает структурированные события прогресса в реальном времени по Сигналу. R, чтобы подключенные клиенты могли следить за ходом работы.

## Трубопроводные стадии

### Этап 1 — CheckServers

Перед началом любой переводческой работы служба проверяет выполнение всех предварительных условий:

- Раздел конфигурации должен присутствовать и действовать.
- Сервер LibreTranslate должен отвечать в пределах допустимой задержки.
- Список языков, доступных на сервере перевода, вычитается.
- Настроенный язык по умолчанию должен присутствовать в этом списке.
- Отсутствующие локальные файлы JSON для любого поддерживаемого языка создаются автоматически.

Если какая-либо проверка не удалась, трубопровод немедленно останавливается и посылается сообщение.

### Этап 2 - Трансляционные страны

Названия стран синхронизируются из каталога (только для чтения) в словари локализации JSON.

- Если язык приложения по умолчанию является английским, каждое название страны хранится без перевода.
- Если язык по умолчанию является каким-либо другим языком, английское название страны сначала переводится на этот язык, и результатом становится запись в словаре по умолчанию.
- После обновления словаря по умолчанию каждая недостающая страновая запись в каждом словаре целевого языка переводится и сохраняется ** немедленно на один язык **.
- Уже переведенные записи сохраняются без изменений.
- Если перевод не выполняется, сервис задерживается до 3 раз с 30-секундными задержками, прежде чем перейти на следующий язык.

### Стадия 3 - Перевод JsonFiles

Сервис сравнивает текущий словарь локализации по умолчанию со снимком, сохраненным из предыдущего запуска:

- ** Добавленные ключи** — записи, присутствующие в текущем по умолчанию, но отсутствующие на снимке, — переводятся на каждый целевой язык, который еще не имеет ручной записи для этого ключа.
- ** Снятые ключи** — записи, присутствующие в снимке, но отсутствующие в текущем по умолчанию — удаляются из каждого словаря целевого языка.
- Ручные переводы всегда имеют приоритет. Если целевой словарь уже содержит значение для ключа, эта запись остается неизменной независимо от того, что говорит источник.
- **Each target language dictionary is saved immediately after its translations complete**, rather than waiting for all languages to finish.
- Если перевод не подходит для конкретного языка, сервис автоматически перезагружается. Только постоянные ошибки (например, неподдерживаемый язык) приводят к пропуску этого языка.
- После запуска текущий словарь по умолчанию сохраняется в качестве нового снимка для следующего сравнения.

Все словари всегда хранятся с алфавитно отсортированными ключами и вложенным JSON для удобства чтения.

### Этап 4 - Переводы МаркдаунФайлы

Сервис использует корни сконфигурированной документации (по умолчанию: ) и обрабатывает каждый исходный файл рекурсивно:

1. Содержимое исходного файла считывается и вычисляется хеш SHA-256.
2. Файл, расположенный рядом с исходным кодом, отслеживает состояние перевода на один язык, на один блок, что позволяет ** увеличить повторный перевод ** только неудачных блоков.
3. Сохраненный хэш предыдущего запуска (сохраненный в файле рядом с исходным файлом или во временном резервном местоположении) сравнивается с текущим хэшем.
4. Для каждого целевого языка соответствующий файл также проверяется на структурную целостность.
5. Любой целевой файл, который отсутствует, имеет устаревший хеш, не валидируется структура или содержит нетранслируемые блоки, выстраивается в очередь для повторного перевода.
6. **Каждый целевой язык переводится и сохраняется независимо** — если чешский язык успешен, но французский не удаётся, чешский файл всё равно записывается на диск.
7. Успешно переведенные файлы проверяются на структурный паритет с источником (равные подсчеты заголовков, элементы списка, блоки кода, блокквоты, ссылки, жирные / итальянские маркеры и HTML-теги) до того, как они будут записаны на диск.
8. Если все целевые файлы для источника успешны, новый хэш хранится рядом с источником. Если запись рядом с источником не удается (например, в развертываниях только для чтения), хэш возвращается во временный каталог.
9. Если какой-либо целевой перевод не валидируется, метаданные помечают эти блоки как непереведенные, поэтому они перепроверяются в следующем запуске.

### Стадия 5: Сберегательные результаты

Консолидированный собирается и публикуется. Он включает в себя:

- UTC запускает и завершает временные метки.
- Счета сохраненных локальных файлов JSON, сохраненных файлов Markdown, сохраненных хэш-файлов и резервных хеш-файлов.
- Ошибки хранения, собранные во время выполнения.
- Статистика перевода на язык (переведенный счет, пропущенный счет, подсчет ошибок).

## Логика повторного перевода

Трубопровод реализует два уровня устойчивости:

### Stage-level retry (перевод)

- Если запрос на перевод не выполняется после внутренних запросов LibreTranslate, выполняется до 3 дополнительных запросов на уровне этапа с 30-секундными задержками.
- Маскировщик места: Названные заполнители () в тексте временно заменяются безопасными токенами () перед переводом и восстанавливаются после этого, обеспечивая правильную грамматику на целевых языках.

### Валидация языка

- Перед переводом на целевой язык служба проверяет, поддерживает ли язык сервер перевода.
- Неподдерживаемые языки пропускаются с предупреждением, предотвращая повторные неудачные попытки.

### Обновление уровня блоков Markdown

- Переводы с разметкой выполняются по блокам (заголовки, абзацы, пункты списка).
- Если отдельный блок не выполняет перевод, он помечается как непереведенный в файле метаданных и перепроверяется при следующем запуске трубопровода.
- Сервис отслеживает состояние каждого языка, каждого блока в файлах рядом с каждым исходным файлом Markdown.

## Коды ошибок

Ошибки сообщаются с использованием унифицированного числа, сгруппированного в диапазоны:

Диапазон
|-------|----------|
1000-1999
2000-2999
3000-3999
4000-4999
5000-5999

Каждая ошибка в отчете несет идентификатор источника (языковой код, путь к файлу или сценическое имя), код ошибки и считываемое человеком сообщение.

## Прямая панель перевода

Проект Server включает в себя страницу администратора, которая подключается к концентратору SignalR и отображает все события конвейера в режиме реального времени.

- Отображает состояние соединения, количество сообщений и таблицу обновлений всех событий.
- Цветные строки: синий для начала сцены, зеленый для завершения, красный для ошибок.
- Поддерживает очистку корма и экспорт всех сообщений в JSON.
- Авто-соединяется с экспоненциальным отключением, если соединение падает.

## Принципы проектирования

- **Modularity**: Each translation concern is isolated in its own service for maintainability and testability.
- ** Повышенная настойчивость**: Словари и файлы Markdown сохраняются на одном языке сразу после перевода, снижая давление в памяти и обеспечивая более раннюю обратную связь.
- **Resilience**: Multiple retry levels (HTTP, stage, block) ensure transient failures do not block the pipeline.
- ** Государственное отслеживание**: Метаданные каждого файла () и хеш-файлы позволяют выполнять точную дополнительную работу при последующих запусках.
- **Наблюдение в реальном времени**: Каждая значительная операция сообщается через SignalR для мониторинга и отладки.
- **Переводы всегда имеют приоритет перед автоматическими дополнениями. **
