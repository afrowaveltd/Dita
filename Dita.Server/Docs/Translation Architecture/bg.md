# Превод: Архитектура

Този документ описва модулната архитектура на автоматичната преводна система на Дита, въведена с цел подобряване на устойчивостта, устойчивостта и устойчивостта.

## Проектни цели

Образуването се обърна към няколко проблема с оригиналния монолитен дизайн:

- **Разделяне на притесненията **: Всеки превод домейн (страни, JSON речници, Markdown) е изолиран.
- ** Непрекъснато постоянство **: Файловете се записват на език веднага след превод, намаляване на използването на паметта и осигуряване на по-ранни резултати.
- ** Устойчивост **: Множество ретри нива се справят преходни неуспехи без блокиране на целия тръбопровод.
- ** Възможност **: Всяка значителна операция се отчита чрез SignagerR за наблюдение в реално време.
- ** Разширяване **: Новите цели за превод могат да бъдат добавени чрез прилагане на единен интерфейс.

## Разлагане на услугата

### Backend Translation Service (оркестър)

** Отговорности **:
- Управление на жизнения цикъл на тръбопровода (начало, завършване, обработка на грешки)
- Контрол на валутните курсове на базата на семафора (предотвратява припокриващи се писти)
- Утвърждаване на сървър (постоянност, езикова наличност, конфигурация)
- Делегация на подуслуги

** НЕ съдържа **:
- Логика на превода
- Файл I/O за специфични формати
- Логика на възприятията

### Услугата за превод на страните

** Отговорности **:
- Четене от директорията
- Синхронизиране на имената на страните в речника по подразбиране
- Преведи липсващите имена на държавата на целеви език
- Запис на всеки целеви речник веднага след превода

**Key behaviors**:
- Ако езикът по подразбиране е английски: имена на държави съхранени като е
- Ако езикът по подразбиране е друг: английски имена преведени на езика по подразбиране първо
- Всеки език се обработва независимо от собствения си цикъл

### Локализация TranslationService

** Отговорности **:
- Откриване на добавените/преместваните ключове чрез сравняване на текущия речник по подразбиране с предишната снимка
- Преведи добавени ключове на всеки целеви език
- Изтриване на ключове от всеки целеви език
- Запис на снимка за следващото сравнение

**Key behaviors**:
- Ръчно преводи винаги вземат приоритет (никога презаписани)
- Добавянето на ключове се превежда и записва на език веднага
- Премахнатите ключове се изтриват на език незабавно
- Snapshot се запазва само след като всички езици завърши успешно

### ДокументиУслуги за превод

** Отговорности **:
- Walk конфигуриран Markdown корени рекурсивно
- Откриване на променени изходни файлове с помощта на SHA-256 hashes
- Проследяване на статус на блок превод в
- Преведи блок по блок с рестартиране на блок
- Валидиране на структурата за маркиране след превод
- Запис на всеки целеви езиков файл независимо

**Key behaviors**:
- Подробност на блоковото ниво: позиции, параграфи, позиции от списъка се превеждат отделно
- Следи от метаданни, които са успели/неуспешни на език
- Неуспешни блокове се опитват отново в следващия пробег без препредаване на успешни блокове
- Заверяване на структурата осигурява преброяване, списъци, кодови блокове и др. източник на съвпадение

## Стратегия за ретрия

Системата се прилага на три нива:

### Ниво 1 (LibreTranslate Service)

- До 5 опита с експоненциално отстъпление (1s, 2s, 3s, 4s, 5s)
- Мрежови прекъсвания, 5xx грешки и преходни неуспехи
- Вградена в конфигурацията на HTTP клиент

### Ниво 2 Сцена (Услуги за превод)

- До 3 опита с 30-секундно забавяне
- Пре-двигатели цялата заявка за превод след HTTP ниво retries са изчерпани
- На това ниво се прилага маскировка и реставрация

### Ниво 3 Блок (Authorities Translation Service)

- Отделни блокове за отбелязване, които не работят, са маркирани в метаданни
- Автоматично рестартиране на следващия тръбопровод
- Успешните блокове никога не се препревеждат

## Поток на данни

### Превод на речник JSON

```
[Default Dictionary]
       ↓
[Compare with Snapshot]
       ↓
[Detect Added/Removed Keys]
       ↓
For each target language:
   ├─ Load existing dictionary
   ├─ Apply removals
   ├─ Translate additions (with retry)
   └─ Save dictionary immediately
       ↓
[Save new snapshot]
```

### Маркиране на превод

```
[Source File]
       ↓
[Compute Hash]
       ↓
[Compare with stored hash]
       ↓
[Load translation metadata]
       ↓
For each target language:
   ├─ Extract translatable blocks
   ├─ For each block:
   │   ├─ Check metadata (already translated?)
   │   ├─ Translate with retry
   │   └─ Mark success/failure in metadata
   ├─ Reconstruct Markdown
   ├─ Validate structure
   ├─ Save target file
   └─ Save metadata
```

### Превод на името на страната

```
[countries.json]
       ↓
[Build set of country keys]
       ↓
[Update default dictionary]
       ↓
For each target language:
   ├─ Find missing country entries
   ├─ Translate each missing entry (with retry)
   └─ Save dictionary immediately
```

## Устойчивост на държавата

### Изстрели

- ** JSON **: Съхранява се във файл до речника по подразбиране (името варира от доставчика на съхранение)
- **Предполагам **: Позволява инкрементален синхронизация чрез проследяване на това, което е имало в предишния пробег

### Хаш файлове

- ** Маркдаун **: до изходния файл
- ** Fallback **: ако основното място е само за четене
- **Предполагам **: Детективи на изходните промени, за да се избегне ненужната препредаване

### Метаданни за преводи

- ** Маркдаун **:
- ** Contents **:
  - Източник на съдържание хашиш
- На езиков блок статус (заливане на boolians)
- Последна актуализация
- **Предполага **: Позволява частична препредаване само на неуспешни блокове

### Съхранение на място

- **Архив **:
- ** Contents **: Речник на ключовете за притежателя име-стойност двойки
- **Предположение **: Осигурява стойности по подразбиране за назоваваните притежатели в заявлението

## Точки на разширение

### Добавяне на нова цел превод

1. Създаване на нов интерфейс с
2. Изпълнение на интерфейса със специфична логика
3. Регистрирайте се в DI контейнер
4. Инжектиране в конструктор
5. Обаждане след съществуващи етапи

### Политика за персонализиране

Параметри на конструктора:

```csharp
services.AddSingleton<TranslationRetryService>(
    sp => new TranslationRetryService(
        sp.GetRequiredService<ILibreTranslateService>(),
        sp.GetRequiredService<IPlaceholderService>(),
        sp.GetRequiredService<ILogger<TranslationRetryService>>(),
        stageMaxRetries: 5,        // More retries
        stageRetryDelaySeconds: 60  // Longer delays
    ));
```

### Потребителска обработка на държателя

Прилагане за промяна на синтаксиса или съхранението на държателя:

```csharp
public class CustomPlaceholderService : IPlaceholderService
{
    // Use {{name}} syntax instead of {name}
    // Store in database instead of JSON file
    // Encrypt sensitive placeholder values
}
```

## Стратегия за изпитване

### Изпитвания на единица

Всяка подобслужване е независимо изпитана:

- Мок за симулиране на успеха/провала
- Подиграване за проверка на докладването
- Използване на временни директории за файл I/O
- Проверка на поведението за запазване на езика

### Изпитвания за интеграция

- Пълен тръбопровод с реална (локална) LiberTranslate случай
- Проверка на сигнала R съобщения се доставят на свързани клиенти
- Изпитване на едновременно изпитване (семафор)
- Валидиране на структурата за маркиране след превод

### Изпитвания от край до край

- Спусък превод чрез API или график
- Проверка на всички целеви езикови файлове са създадени/нагоре
- Проверка на файловете с метаданни съдържа правилен статус на блок
- Потвърдете титулярите са запазени в преводите

## От съображения за ефективност

- ** Паметта **: Спасяването на езика предотвратява задържането на всички речници в паметта
- **Диск I/O **: Метаданни файловете добавят малки режийни разходи, но позволяват допълнителна работа
- **Network **: Последователна обработка с throtling предотвратява съкрушителната LibreTranslat
- **CPU **: SHA-256 hashing and regex валидиране са бързи в сравнение с превод латентност
- **SignalR**: Леки съобщения, без компресиране на полезен товар, необходими за типични доклади

## Миграция от монолитен дизайн

Оригиналът съдържаше цялата логика в един клас. Пътят на миграция:

1. Извличане на национална логика →
2. Извличане JSON логика →
3. Екстракт Маркдаун логика →
4. Извличане на сигнал R публикуване →
5. Извличане логика retri →
6. Опрости оркестъра само на делегация

Всички съществуващи интерфейси () остават непроменени. Потребителите на газопровода не виждат промени.
